Grounding Context

The current application has a substantial foundation: editing, piano-roll MIDI, built-in mixing and automation, import, WAV export, save and recovery. The live handoff records the Usable-song milestone on packaged 7a1b0ad, followed by thirteen layout improvements. This review checked current source and recorded evidence; it did not launch the app, inject desktop input, perform fresh hardware measurements or run a new local build.

Current source CI run 41727515729 completed successfully in all ten jobs, including Windows/macOS/Linux builds and tests, RTSan, TSan and packaging. That verifies those gates, not newly measured gesture latency or a new hardware result.

Two source-level opportunities are concrete: committed MIDI changes take the full playback replacement path, and import/stretch preparation is synchronous. Their actual latency and audible impact remain to be measured. Three musical limitations are explicit: head-tempo MIDI conversion, a head-tempo/metre metronome, and incomplete MIDI loop/tempo-map export.

Important correction from independent verification

MIDI note dragging already commits once at mouse-up as one undo transaction. There is no basis for claiming a full durable save on every pointer movement. Transport is restored after engine replacement; a lost playhead is also not an established bug.

Priorities remain the owner's: a full general-purpose DAW on C++/JUCE and the existing engine, editing first, MIDI written in the piano roll, voiceover as the recording use case, WAV as the final format. These recommendations are a discovery artifact; they do not amend Accepted ADRs or promote a new implementation mandate.

Method: 40 raw ideas across five passes and six perspectives; 26 after deduplication; a fresh evidence check and final arbitration produced seven directions. Each generating pass had up to five targeted verification operations; the combined-frame pass shared that budget, so scrutiny was not uniform. Current source and policy outrank historical notes. The institutional solutions store has one early build/CI note; its relevant lesson is keeping pure checks independent of device setup. Slack was not consulted.

1. Keep playback continuous while editing MIDI

A committed note edit should update the playing MIDI while instruments and effects keep their state. The current changed-MIDI path builds and installs a replacement PlaybackEngine.

Basis
direct: UiAppModel.h:12089 rejects changed MIDI from live placement; :12188 creates another engine, :12211 writes the project snapshot, :12224 replaces playback. The code restores Transport afterward; lost playhead is not an established bug. Note drags already commit once on mouse-up (PianoRollInputComponent.h:763,939-940); this is not a per-pointer-event persistence problem.
Rationale
This targets the central way Dan composes. Measure held notes, effect tails and edit latency during a playing loop, then extend live publication if the measurements confirm the expected reset cost.
Downsides
Engine and Audio-thread work needs an ADR/critic and RTSan/TSan coverage. Note-on/off transitions, controller state, undo and existing save guarantees must remain exact. No new audible failure was measured in this review.

2. Keep controls responsive during imports and stretching

Decode and prepare long media in cancellable background work, keeping the current sound until a new result is ready. Reuse identical prepared stretches across duplicated Clips when complete input identities match.

Basis
direct: MainComponentBrowser.cpp:405-417 directly decodes before import. UiAppModel.h:13830-13877 synchronously prepares uncached source windows; :13852 also keys reuse to Clip identity. external: JUCE ThreadPool supports background jobs, but cancellation is cooperative.
Rationale
Ordinary paint timings do not measure long import or stretch operations. This foundation also helps later tempo-follow and large stem sessions.
Downsides
Measure first. Cancellation, stale results, project replacement, atomic adoption and source ownership need deliberate handling. Reusing results must include source/view rate, window, algorithm version and all relevant settings.

3. Make the musical clock agree everywhere

Make the grid, new MIDI, metronome and interchange agree on the full Tempo map. Preserve an explicit fixed-time choice and existing saved Project meaning. MIDI export should include Clip repeats and all supported tempo/meter changes.

Basis
direct: UiAppModel.h:3377-3398 converts MIDI quarters at head tempo into SampleLocked Clips; :13902-13910 configures click from head tempo/meter. Midi.h:651-675 already distinguishes SampleLocked and TempoLocked projection. UiAppModel.h:3545 omits loop unrolling; :3620-3624 supplies only head tempo/meter to export.
Rationale
Tempo ramps are already supported, so consistency closes gaps inside existing workflows. The first small correction can be the metronome following an existing tempo/meter change; MIDI interchange matters less than WAV to this user but shares the same timing concern.
Downsides
This is architecture/saved-data-sensitive. Do not silently reinterpret legacy SampleLocked Clips or alter accepted formats. Define migration/default behavior through an ADR; verify musical positions against independently computed expectations.
Coherent musical timingConfidence 90%Complexity High

4. Let musical audio follow the song tempo

Give Clips an explicit musical or fixed-time policy. Start with known-tempo loops fitting a chosen number of bars and following tempo edits; keep voiceover fixed by default. Internal transient/warp markers can follow later.

Basis
direct: STATUS.md:17-18 records no audio tempo-follow or audio quantize/warp, despite manual time-stretch. external: Logic Flex & Follow separates fixed audio, tempo following and bar/beat conformance.
Rationale
This turns tempo editing into a useful arrangement tool while protecting spoken audio. It is a feature expansion, separate from correcting the existing musical clock.
Downsides
Saved-data and rendering decisions need an ADR, sound-quality fixtures and render/live agreement. Source-tempo detection and transient warping are larger follow-ups, not prerequisites for a known-BPM first step.

5. Arrange related Tracks and sections together

Add linked edit groups with clear corresponding-Clip rules and collapsible Track organization. A later section operation could move or duplicate a Verse or Chorus together with the affected Clips and automation.

Basis
direct: STATUS.md:19 records no folder Tracks or groups. external: Ardour documents exact matching or overlapping corresponding-region selection. reasoned: reusable target sets and transactions prevent alignment/undo behavior from diverging across commands.
Rationale
Layered instruments and stem sessions need repeated coordinated edits. This reduces bookkeeping while making song structure easier to manipulate.
Downsides
Groups, folders, mixing links and section operations are different scopes. Start with a precise linked-edit behavior; define edge-crossing Clips, automation boundaries, hidden Tracks and one-step undo before broadening.
Arranging/composition workflowConfidence 85%Complexity Medium

6. Show the other parts while writing MIDI

Show chosen reference Tracks as faint, non-editable ghost notes behind the active MIDI Clip, with a used-pitches-only view. Keep one unmistakable active editing target.

Basis
direct: UiAppModel.h:4319 keeps one selectedMidiClipId_; UiPianoRollSurface.h:447 projects one selected Clip. external: Logic documents multi-track and collapsed-note piano-roll views. Existing scale assist and Sampler drum view already exist and are not proposed as new features.
Rationale
Dan writes notes with the mouse. Seeing bass against chords or a melody against harmony reduces Track switching and makes composition more direct.
Downsides
Reference identity and active selection must stay clear; viewport, overlapping notes and keyboard accessibility need a simple smoke check. Validate absence with a wider symbol search before implementation; a single selected-Clip field alone cannot establish every UI capability.

7. Close the first-playback and intermittent editing faults

Reproduce and diagnose the recorded launch-time Underrun and intermittent SS3 editing failure. Capture the failing sequence, callback timing, state and input delivery so a specific fix gets a regression check.

Basis
direct: STATUS.md:56-64 records a launch glitch with unknown cause and an SS3 failure followed by clean runs. docs/evidence/2026-10-13-usable-song-drives-and-hardware.json retains the raw outcome. These are historical observations; this review did not reproduce them.
Rationale
First playback and basic editing deserve a supported explanation when they fail. Existing Session drives, State probe and audio checks can investigate without making Dan the routine tester.
Downsides
The two failures may have unrelated causes, and later successful runs do not explain either. Native input/audio proof still needs the correct isolated input session or actual device route; safe code/tests can continue independently. Reuse the existing tooling and ADR-0078 cadence.
