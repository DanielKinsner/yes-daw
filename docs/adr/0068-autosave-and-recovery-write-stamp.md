# 0068. Autosave on the model's edit serial, with a write-stamp that tells recovery what the bundle lacks

- **Status:** Accepted (2026-10-07, after a design workflow — three designs, three judges — and three separate agent
  critic rounds; every blocker resolved below)
- **Date:** 2026-10-07
- **Deciders:** build agent (proposer); a design workflow (three designs, three judges); separate agent critics (three rounds)
- **Related:** ADR-0012 (SQLite bundle: WAL + `synchronous=NORMAL`; "autosaved" is explicitly not "saved"; the macOS `F_FULLFSYNC` and `synchronous=FULL`-at-Save escalations ADR-0012 names remain open — this ADR neither relaxes nor delivers them; the append-only `project_write_stamp` migration lands under the ADR-0012 "add-and-deprecate, never drop" rule); ADR-0019 (a hard kill mid-edit recovers to the last autosave with no corruption; snapshots are bundle-shaped, fsynced, with asset bytes carried in before acceptance — unchanged); ADR-0035 (Restore / Discard are the only user choices over a validated snapshot — unchanged; the two-button contract preserved; the shell's prompt text gains the saved-side counts, below); ADR-0036 (recorded Takes and WAV Assets validated by the bundle's open-time standard — unchanged); ADR-0049 (the autonomy scope under which this implementation ADR lands); ADR-0060 (the Project bundle is always current — "unsaved" is a model marker; Save As and Save a Copy exclude `autosave/` from the copy — unchanged, applied); H17 CP4 ([`docs/plans/2026-07-03-h17-distribution-alpha-plan.md`](../plans/2026-07-03-h17-distribution-alpha-plan.md) — autosave scheduling is ON by default, 30 s cadence, on the control-tick Timer — unchanged); the Usable-song milestone ("recover interrupted work without guessing what survived") and SS-6 step 6 in [`docs/plans/2026-09-01-real-daw-ground-up-plan.md`](../plans/2026-09-01-real-daw-ground-up-plan.md).

## Context

**The bundle is already always current.** Every undoable edit funnels through four `UiAppModel` adopt paths — `adoptPlacementEditLive` (`src/ui/UiAppModel.h:11745`), `adoptEditedProject` (`:11798`), `adoptEditedProjectWithoutPlaybackRebuild` (`:11869`), `adoptScalarEditLive` (`:11963`) — and each calls `bundleDb_.writeProjectSnapshot (nextProject)` (`:11775`, `:11835`, `:11875`, `:11969`) **before** swapping `project_` and **before** advancing `editSerial_`; a failed write refuses the edit. `dispatchUndo` (`:12122`) and `dispatchRedo` (`:12164`) write through the same adopt paths. `saveProjectBundle` (`:2026-2044`) writes the same snapshot a redundant second time and its only distinct effect is `lastSavedEditSerial_ = editSerial_`. `hasUnsavedChanges()` is `editSerial_ != lastSavedEditSerial_` (`:2051`), and the close prompt is honest: "Save this state as your saved version before closing? (Every edit is already stored in the project bundle.)" (`src/ui/MainComponent.cpp:2077-2078`; `src/ui/MainComponentProject.cpp:119`). Four more paths also call `writeProjectSnapshot` directly: `setProjectScale` (`:4998`), the loop-region persist (`:12766`), the locate-point persist (`:12830`), and the template write (`:3025`); `saveProjectBundleAs` writes through `writeBundleCopy` (`:2202`) and `restoreAutosaveSnapshot` writes through `targetDb.writeProjectSnapshot` (`src/persistence/AutosaveRecovery.h:305`).

**What the autosave is for.** ADR-0012 states durability honestly: `synchronous=NORMAL` + WAL survives a clean process kill but not a power cut; "autosaved (crash-recoverable)" is explicitly not "saved (power-loss-durable)." ADR-0019 pins the recovery contract: a hard kill mid-edit recovers to the last autosave with no corruption; the snapshot is bundle-shaped, fsynced, with asset bytes copied before acceptance (`AutosaveRecovery.h:218-255`; two-rename publish at `:160-214` with `autosave/last.previous` as rollback slot). The autosave is the independent, validated fallback for the hard-kill-mid-WAL-write and the macOS power-cut windows the always-current bundle cannot cover on its own.

**The shipped app never writes one.** `MainComponent::serviceUiTick` calls `appModel.writeAutosaveTick()` every 30 s (`AutosaveSchedulePolicy{ enabled=true, intervalMs=30000 }`). `writeAutosaveTick` (`UiAppModel.h:2286-2306`) delegates to `persistence::writeAutosaveFromControlTick` (`src/persistence/PlaybackAutosave.h:16-28`), which early-returns on `! playback.needsAutosave()`. `PlaybackEngine::needsAutosave()` is `editRevision_ != autosavedRevision_` (`src/engine/PlaybackEngine.h:444`); `markProjectEdited()` is declared at `:449` and `grep -rn 'markProjectEdited' src tests` finds exactly one caller — `tests/playback_tests.cpp:1324`. No production path flips the counter. `needsAutosave()` is permanently false; `autosave/last.yesdaw` is never written; `detectAutosaveRecoveryPrompt()` (`UiAppModel.h:11117-11129`) has nothing to offer. SS-6 step 6 cannot pass. Found by the SS-6 drive on 2026-10-07.

**Latent hazards once writes start.** Three paths are correct in prose but silent in code:
- Save, Save As, Save a Copy, and the two "Don't Save" prompts never call `discardAutosaveSnapshot` (`UiAppModel.h:2026-2256`; `MainComponent.cpp:2062-2093`; `MainComponentProject.cpp:103-132`). A save-then-reopen would raise a prompt over work the bundle already holds, and Restore would overwrite a newer saved E2 state with an older autosaved E1 via `restoreAutosaveSnapshot → targetDb.writeProjectSnapshot(recovered)` (`AutosaveRecovery.h:284-309`).
- `context_.autosaveRecoveryPending` gates the two recovery actions (`src/ui/UiActions.h:1522`) but nothing in `writeAutosaveTick` consults it; the next tick after the prompt rises would overwrite the pending snapshot and destroy the user's choice.
- `tests/app_smoke_tests.cpp:220-251` ("H17 CP4 … `writeAutosaveTick` is a safe no-op") and the SS-6 probe test in `tests/project_lifecycle_tests.cpp:264-316` both lock the broken behaviour green: neither asserts `autosave.writes > 0` after an edit.

**One source of truth is already here.** `editSerial_` and `lastSavedEditSerial_` already advance on every undoable edit and on Save; `attachProjectBundle` resets both to 0 (`:12691-12692`). A third serial completes the trio. The engine's parallel counter adds nothing the model does not already know, and the bug this ADR fixes is exactly one path (edits → engine counter) that was never wired.

**What recovery can't tell today.** `detectAutosaveRecoveryPrompt` raises the question whenever a valid snapshot sits beside the bundle, with no way to tell "the snapshot holds something the bundle lacks" from "the snapshot is stale." A clean Save-then-reopen would ask about work the bundle already holds; a torn `discardAutosaveSnapshot` after a Save would leave a stale slot that Restore would roll back onto a newer saved state. Serial equality is enough in the model (§2–§4), but a persistent, in-bundle stamp is needed to carry the same signal across a process restart; the bundle already carries a user_version and an append-only schema (`ProjectBundle.h:41, 1523-1557, 950`), so a singleton stamp fits that pattern.

## Compatibility with Accepted ADRs

This is an implementation ADR under ADR-0049; it rewrites no Accepted ADR, and amends by stating compatibility:

- **ADR-0012:** no PRAGMA change, no change to the WAL + `synchronous=NORMAL` live mode. A new, append-only schema version lands under ADR-0012's "add-and-deprecate, never drop" rule (§5). The macOS `F_FULLFSYNC` and `synchronous=FULL`-at-Save gaps ADR-0012 names remain open; see **Follow-ups**.
- **ADR-0019:** the snapshot shape, asset-copy law, two-rename publish and the open-time validator are unchanged. The reliability harness (`YesDawReliabilityCheck`, `tests/reliability_tests.cpp`) is unchanged.
- **ADR-0035:** Restore and Discard remain the only user choices, both scriptable, both over a validated snapshot. The action-registry gating by `requiresAutosaveRecovery` (`UiActions.h:515, 1522`) is unchanged. The prompt is already non-modal (the UI timer runs; writes elsewhere are refused by the pending gate, §2). The shell's prompt text gains the saved-side counts (§6) — a strict addition to the ADR-0035 wording, no change to the buttons.
- **ADR-0036:** Takes and recorded WAV Assets are still validated against the bundle's open-time standard inside the snapshot.
- **ADR-0060:** the always-current-bundle law stands; Save As and Save a Copy still exclude `autosave/` (`UiAppModel.h:2149, 2168`); Save a Copy still leaves the source current.

## Decision

### 1. The model owns the "edited since the last autosave" record

Add two new fields on `UiAppModel` (control thread, same lifetime as the two existing serials at `UiAppModel.h:13534`):

- `lastAutosavedEditSerial_` — `std::uint64_t`, 0 at construction; reset to 0 by `attachProjectBundle` alongside `editSerial_` and `lastSavedEditSerial_` (`:12691-12692`); set by a successful autosave write and by a retirement call.
- `autosaveSkips_` — int, bumped on each tick that returned `ok()` without writing because the pending-prompt gate was up. Exposed on the probe as `autosave.skips` so a drive can distinguish "nothing was due" from "writes were deliberately gated."

### 2. Due predicate: write when there is un-autosaved, unsaved work and no prompt is pending

`UiAppModel::writeAutosaveTick` returns `ok()` without writing when any of the following hold, in order:

1. No bundle is open or `playback_` is null (unchanged, `UiAppModel.h:2287-2288`).
2. `context_.autosaveRecoveryPending` is true — the pending snapshot IS the user's lost work, and overwriting it would destroy ADR-0035's choice. Bump `autosaveSkips_`.
3. `editSerial_ == lastSavedEditSerial_` — the bundle already holds the saved state; a snapshot would be older or equal, and the recovery predicate would discard it silently anyway (§5).
4. `editSerial_ == lastAutosavedEditSerial_` — the current snapshot already holds this edit; the autosave MUST NOT write when the stamp says nothing changed since the last autosave.

Otherwise, capture `snapshotSerial = editSerial_`, call `persistence::writeAutosaveSnapshot (bundleDb_, project_)` directly (ADR-0019 publish, unchanged except for the stamp carry in §5). On `ok()`: `lastAutosavedEditSerial_ = snapshotSerial`, `++autosaveWrites_`, record `lastAutosaved_` counts. On error: `++autosaveFailures_`, set a sticky `autosaveNotDurable_` flag (new, cleared by the next successful write; exposed as `autosave.notDurable` on the probe), and report "Autosave failed" on the shared status line (`statusLineText_`, unchanged path). `lastAutosavedEditSerial_` stays put so the next due tick retries the same tail — a transient I/O error does not escalate into a cadence of lost work.

The engine's `needsAutosave` / `markProjectEdited` / `markAutosaved` and `persistence::writeAutosaveFromControlTick` are no longer the trigger. They stay in place for one commit window with their one test caller (`tests/playback_tests.cpp:1318, 1324, 1326`) and are removed in a separate cleanup slice (§Checkpoints cp7); this ADR does not delete them, so each checkpoint can be reviewed in isolation.

The cadence (30 s), the on-by-default policy, the Session-drive seams `MainComponentFileChoices::autosaveIntervalMs` and `YESDAW_AUTOSAVE_INTERVAL_MS` (`src/ui/MainComponentProbe.cpp:1719-1722`), and `setAutosaveIntervalMs` (`UiAppModel.h:2311`) are unchanged.

### 3. A successful save retires its autosave

- **Save** (`saveProjectBundle`, `UiAppModel.h:2026-2044`): on `writeProjectSnapshot().ok()`, after `lastSavedEditSerial_ = editSerial_`, call `persistence::discardAutosaveSnapshot (bundlePath_)` and set `lastAutosavedEditSerial_ = editSerial_`. The bundle now holds everything the autosave did. A failed retirement does not fail the Save (the Save itself succeeded and is durable); the failure reports to the status line and sets `autosaveNotDurable_`. A torn retirement is caught silently on the next open by §5's stamp comparison, so this ADR does not need a second guard here.
- **Save As** (`saveProjectBundleAs`, `UiAppModel.h:2221-2256`): capture `previousBundlePath = bundlePath_` **before** `bundleDb_ = std::move (reopened)`. After the open-handle swap succeeds and `lastSavedEditSerial_ = editSerial_` is set, call `discardAutosaveSnapshot (previousBundlePath)` and set `lastAutosavedEditSerial_ = editSerial_` on the new bundle. The destination's own `autosave/` is empty by ADR-0060's exclusion. A failed retirement of the previous bundle does not fail the Save As; the failure reports to the status line.
- **Save a Copy** (`saveProjectBundleCopy`, `UiAppModel.h:2259-2277`): unchanged. The open bundle still carries the unsaved tail and must keep its own autosave accurate; the copy itself has none (ADR-0060).

### 4. Deliberate "Don't Save" retires the autosave; interruption does not

A new model API, `UiAppModel::retireAutosaveOnDontSave()`, calls `persistence::discardAutosaveSnapshot (bundlePath_)` and sets `lastAutosavedEditSerial_ = editSerial_`. It is the single owner of the retirement side effect at Don't Save.

Two shell confirm paths call it before the project leaves the window, each at the exact point they already observe the "Close without saving" / "Don't Save" choice:

- `MainComponent::confirmClose` (`src/ui/MainComponent.cpp:2062-2093`), close branch (choice `== yesdaw::ui::kCloseChoiceClose`, `:2093`).
- `MainComponentProject::confirmReplaceProject` (`src/ui/MainComponentProject.cpp:105-132`), close branch (choice `== kCloseChoiceClose`, `:131`) — one site covering New and Open.

Rationale: recovery is for interrupted work; the user named this state abandoned. The bundle itself still holds every edit (ADR-0060's always-current law), so Don't Save is a clean-point and autosave decision only, never a data rollback. The existing prompt wording ("Every edit is already stored in the project bundle") stays accurate.

A crash, a hard kill or a power cut writes nothing to this path and leaves the last snapshot in place; the next open goes through `detectAutosaveRecoveryPrompt` and ADR-0035 (unchanged, modulo §5's silent-discard predicate).

### 5. A persistent write-stamp lets recovery offer only what the bundle lacks

An append-only schema migration **v35**, under ADR-0012's add-and-deprecate rule, adds a singleton stamp table to the bundle. The migration is a new entry in `kMigrations` (`src/persistence/ProjectBundle.h:1523-1557`; its `std::array` size goes from 34 to 35), `kCodeSchemaVersion` bumps from 34 to 35 (`:41`), and a new `kSchemaV35Sql` is appended beside `kSchemaV34Sql` (`:1503`):

```sql
CREATE TABLE project_write_stamp (
  singleton_id              INTEGER PRIMARY KEY CHECK (singleton_id = 1),
  write_count               INTEGER NOT NULL DEFAULT 0,
  unresolved_snapshot_stamp INTEGER            -- NULL, or the stamp of a recovery question raised and not yet answered
);
INSERT INTO project_write_stamp (singleton_id, write_count, unresolved_snapshot_stamp) VALUES (1, 0, NULL);
```

`ProjectBundleDb::writeProjectSnapshot` (`:2281`) runs `UPDATE project_write_stamp SET write_count = write_count + 1;` inside the same transaction as the snapshot write — one statement, between the final appends and the existing `COMMIT;` at `:2937` (the `wal_checkpoint(TRUNCATE)` at `:2948` carries no change). Every bundle-write path funnels through `writeProjectSnapshot`, so the stamp advances on every adopt path (`:11775, 11835, 11875, 11969`), on undo/redo (through the adopt paths at `:12122, 12164`), on `saveProjectBundle` (`:2036`), on `setProjectScale` (`:4998`), on the loop-region persist (`:12766`), on the locate-point persist (`:12830`), on `restoreAutosaveSnapshot`'s target write (`AutosaveRecovery.h:305`), on `saveProjectBundleAs`'s copy write (`:2202`), and on the template write (`:3025`).

An autosave snapshot carries the **source** stamp. `writeProjectSnapshot` gains an optional `stampOverride`: when given, the shared-transaction statement sets `write_count = :stampOverride` instead of advancing it, so the value lands in the same `BEGIN IMMEDIATE ... COMMIT` and the same `wal_checkpoint(TRUNCATE)` as every other row of the snapshot. `writeAutosaveSnapshot` (`AutosaveRecovery.h:218-255`) reads `sourceStamp` from `sourceDb.projectWriteStamp()` (a new accessor on `ProjectBundleDb`) and writes the snapshot with `snapshot.writeProjectSnapshot (project, sourceStamp)` (`:236`); the flush of `project.db` at `:242` then makes it durable with everything else before publish. The snapshot reports "the source bundle was at stamp N when I was written." (A separate override UPDATE after the commit would sit in the snapshot's WAL, outside the flushed file - weaker than every other row; rejected below.)

On open, `detectAutosaveRecoveryPrompt` (`UiAppModel.h:11117-11129`) compares:

- **`snapshotStamp <= bundleStamp`** — the snapshot holds nothing the bundle lacks. **Discard silently** via `persistence::discardAutosaveSnapshot (bundlePath_)`, no question raised. Covers the clean Save-then-reopen path and the torn-retirement window (Save succeeded, `discardAutosaveSnapshot` crashed partway).
- **`snapshotStamp > bundleStamp`** — the bundle lost writes (a power cut, a torn WAL). **Raise the prompt** as today, with the saved-side counts added (§6).
- **An unanswered question is asked again.** The prompt is non-modal, so a user can edit (advancing the bundle's stamp) and be interrupted again before answering. When the question is raised, the model records `unresolved_snapshot_stamp = snapshotStamp` in the bundle (a write that does not advance `write_count`); on every open, a snapshot whose stamp equals a non-NULL `unresolved_snapshot_stamp` raises the question **whatever the order of the stamps**; Restore and Discard set it back to NULL — Discard clears the marker before it discards the snapshot (a failure between leaves the snapshot to the stamp comparison, never a marker naming nothing), Restore clears it inside the same transaction that writes the recovered rows (the stamp advance and the clear land together). The marker's own write commits and checkpoints like a snapshot write. Without the marker, the edits made while ignoring the question would silently retire the very snapshot that held the lost work.
- **Nothing but an answer retires a pending snapshot.** While a question is pending, Save, Save As and Don't Save do not discard the autosave (§3, §4): it holds work the bundle lacks, and only Restore or Discard decides it. A Save As while pending leaves the left bundle's snapshot and marker for its next open.

A pre-v35 bundle (no stamp) runs the v35 migration on open; the `INSERT (1, 0)` lands the stamp at 0 with no stamp bump from the migration itself. A pre-v35 autosave snapshot, read through `readAutosaveSnapshot` / `restoreAutosaveSnapshot` / `pickLiveSnapshot`, is opened with `openExistingBundle` which also runs the v35 migration on the snapshot db; its stamp also lands at 0. Both at 0 therefore satisfies the discard predicate (`snapshot <= bundle`), and the pre-v35 autosave is retired silently on first open. **This is the safe default**: the autosave can never roll back newer work in the bundle, because the bundle is already current under ADR-0060 and the pre-v35 autosave at best equals it. The one-time silent discard runs exactly once per pre-v35 bundle on first v35 open.

Shared transaction note. The v35 statement in `writeProjectSnapshot` — the advance, or the autosave's override — **shares** the snapshot write's existing transaction (opened by `BEGIN IMMEDIATE;` at `src/persistence/ProjectBundle.h:2286` and closed by `COMMIT;` at `:2937`), and is checkpointed into `project.db` by the same `wal_checkpoint(TRUNCATE)` (`:2948`) before the autosave's flush (`AutosaveRecovery.h:242`). Fixture and developer autosaves planted against a v34 bundle are retired silently on first v35 open and must be regenerated.

### 6. The recovery prompt names what each side holds

The existing `UiAutosaveRecoveryPrompt` (`UiAppModel.h:340-350`) already carries six counts for the autosaved side (tracks, assets, clips, Takes, MIDI clips, comp segments; built at `:11105-11115`). The shell's prompt text gains the parallel saved-side counts, read from the attached `project_` at prompt-build time:

> "A snapshot of this project was autosaved after your last Save. Restore it, or discard it and keep the saved version?
> Autosaved: {tracks} tracks, {clips} audio clips, {midiClips} MIDI clips, {takes} takes.
> Saved: {tracks} tracks, {clips} audio clips, {midiClips} MIDI clips, {takes} takes."

The "Saved" row reads `project_.tracks.size()`, `project_.clips.size()`, `project_.midiClips.size()`, `project_.recordingTakes.size()` on the already-attached model. The two-button Restore / Discard contract and the action-registry gating by `requiresAutosaveRecovery` (`UiActions.h:515, 1522`) are unchanged. The prompt is non-modal (same as today) and the pending-prompt write gate (§2) stays, so no autosave write runs while the prompt is up.

### 8. CONTEXT.md gains a plain "Save" term and the "autosaved vs saved" distinction

Two entries land in CONTEXT.md as part of cp1, under the project vocabulary:

- **Save** — "Marking the current state as the user's saved version — a clean point in the model, not a flush of unsaved edits (the bundle is always current, ADR-0060). On success, the autosave of the open bundle is retired."
- **Autosaved vs saved** — "The bundle is always current; 'saved' is the user's clean point and 'autosaved' is a validated, fsynced snapshot that recovers the tail across a hard kill or power cut (ADR-0012, ADR-0019). The bundle carries a `project_write_stamp` so recovery offers only what the bundle lacks."

The existing `Autosave snapshot` and `Autosave recovery prompt` entries (`CONTEXT.md:488-495`) stay.

## Consequences

- The shipped app writes autosaves on the real edit path for the first time; ADR-0019's recovery contract holds on the packaged exe for the first time; SS-6 step 6 passes.
- The recovery question appears only when the autosave holds something the bundle lacks: never after a clean session (edit, Save, close, relaunch), never after a plain kill (the bundle holds every edit), and after lost writes (a power cut) - then again on every open until it is answered.
- A clean process kill still loses nothing on Linux/Windows (bundle holds every edit synchronously, ADR-0012); the autosave covers the open-time-integrity-failed window on all platforms (deferred open-side fallback in **Follow-ups**) and the power-cut window on macOS until the ADR-0012 escalation lands.
- A failed autosave write leaves `lastAutosavedEditSerial_` unmoved — the next tick retries the same tail; a transient I/O error does not force a full cadence of lost work beyond its first failure. A persistent failure stays visible through the sticky `autosaveNotDurable_` probe flag.
- A torn retirement — Save succeeds, then `discardAutosaveSnapshot` crashes partway — leaves a stale snapshot that §5 silently retires on the next open; no false prompt reaches the user.
- A pre-v35 bundle with a pre-v35 autosave is retired silently on first v35 open (§5), one time per such pair, and never rolls back newer work.
- `PlaybackEngine::needsAutosave` / `markProjectEdited` / `markAutosaved` and `persistence::writeAutosaveFromControlTick` lose their only live caller; the engine test (`tests/playback_tests.cpp:1294-1335`) is replaced by cp1's model test and the helpers are deleted in cp7.
- `tests/app_smoke_tests.cpp:220-251` ("`writeAutosaveTick` is a safe no-op") is re-grounded on §2's predicate: a safe no-op when nothing is due, a confirmed write when something is. `tests/project_lifecycle_tests.cpp:264-316`'s SS-6 probe test gains `autosave.writes > 0` after an edit.
- One extra UPDATE per `writeProjectSnapshot` and one override UPDATE per `writeAutosaveSnapshot`; the first is a single row inside an existing transaction, the second is a single row before an existing flush. The reliability harness measures the net.
- Save remains one redundant snapshot write (ADR-0012 WAL commit side effect, kept).

## Gates (`[autosave]` — each red on today's code; headless unless named a drive)

- **`[autosave][due]`** (unit, `UiAppModel`): bundle attached, autosave on, `setAutosaveIntervalMs(250)`. (a) No edits: `autosaveWrites_` stays 0 across 10 ticks. (b) One edit: the next due tick writes once, `autosave/last.yesdaw/project.db` exists on disk, `readAutosaveSnapshot` returns a project whose serialized rows hash equal to the current `project_`'s serialized rows, `lastAutosavedEditSerial_ == editSerial_`. (c) Second tick with no further edit: no write (the `editSerial_ == lastAutosavedEditSerial_` branch of §2). (d) Second edit, next tick: one further write. Red today: `writes` stays at 0.
- **`[autosave][save-retires]`** (unit): edit → due tick writes → `saveProjectBundle` → `autosave/last.yesdaw` and `autosave/last.previous` are both gone, `lastAutosavedEditSerial_ == editSerial_`, next tick writes nothing. Red today: Save never discards.
- **`[autosave][save-as-retires]`** (unit): edit → due tick writes → `saveProjectBundleAs(newPath)` → `previousBundlePath`'s `autosave/` is empty, the new bundle's `autosave/` is empty, `lastAutosavedEditSerial_ == editSerial_` on the new bundle, `bundleDb_.bundlePath()` is `newPath` (the swap happened). Red today: Save As never discards.
- **`[autosave][save-copy-keeps]`** (unit): edit → due tick writes → `saveProjectBundleCopy(copyPath)` → the open bundle's `autosave/last.yesdaw` is bytewise equal before and after, the copy's `autosave/` is empty. Red today: no retirement runs (pass vacuously), but after cp3 the test proves Save a Copy still keeps the source autosave.
- **`[autosave][dont-save-retires]`** (unit, both shell paths): wire the test seam `MainComponentFileChoices::confirmCloseUnsavedChanges` to return `yesdaw::ui::kCloseChoiceClose` for close and for the New / Open replace path. Edit → due tick writes → the confirm path runs → `autosave/last.yesdaw` is gone on close and on replace. Red today: no shell call site retires.
- **`[autosave][pending-gate]`** (unit): plant a valid snapshot via the autosave harness helper (`tests/recording_ux_tests.cpp:147-153`), attach the bundle so `detectAutosaveRecoveryPrompt` raises `autosaveRecoveryPending`, make an edit, run 10 ticks: `autosaveSkips_ == 10`, `autosaveWrites_` unchanged from pre-edit, the planted snapshot's `project.db` SHA-256 is unchanged. Then dispatch Discard: next due tick writes once. Red today: `writeAutosaveTick` does not consult the pending flag.
- **`[autosave][round-trip-bundle-newer]`** (unit, through the shipped action dispatch - the clean kill): attach a scratch bundle; edit to E1; the due tick writes the snapshot at stamp S1; edit to E2 with **no** further tick (the bundle is at S2 > S1, the snapshot still at S1); drop the model instance (no close), re-attach the same bundle through the normal open path. ## Alternatives rejected

- **Feed `PlaybackEngine::markProjectEdited()` from every adopt path.** A second, parallel record of "edited" that every edit path must remember to feed — the bug this ADR fixes is exactly one path that was never fed. `replacePlayback` rebuilds the engine on undo and other paths (`UiAppModel.h:13467`); the engine counter starts at 0 after each rebuild. The model's `editSerial_` is already the one truth and already carries across every rebuild.
- **Discard the autosave on every `writeProjectSnapshot` (every edit) rather than on Save.** The autosave would be deleted on the first edit and rewritten on the next due tick — net work the same, but during the cadence window the user has no snapshot, which ADR-0019 says they must.
- **Keep autosaves after Save as rolling backups.** Then every normal session asks a recovery question about work the bundle already holds; Restore would roll a newer saved state back to an older autosaved one. Backups are a separate feature (project history / versioning), out of scope here.
- **Ask on Don't Save whether to keep the autosave.** A second question on a choice the user just made; §4's prompt wording stays accurate.
- **Compare autosave and bundle by filesystem mtime at open and skip the prompt when the bundle is newer.** Second-granularity, clock-skewed, resettable by backup tools and archive restores; cannot distinguish a torn mid-transaction write from a clean later write. The in-schema stamp (§5) is correct for both.
- **Rely on the Save-side retirement alone, with no write-stamp.** A torn `discardAutosaveSnapshot` after a successful Save would leave a stale slot that Restore would roll back onto a newer saved state. The window is small (one `std::filesystem::remove_all` of a two-file folder), but non-zero, and the fix is a single-row stamp inside an existing transaction.
- **Stamp inside its own transaction, not the snapshot's.** A `writeProjectSnapshot` whose snapshot committed but whose stamp UPDATE failed would leave the bundle one step ahead of its real stamp, and the next open could mis-classify a legitimate autosave as stale. The §5 shared transaction fails them together.
- **Carry the source stamp with a separate override UPDATE after `writeProjectSnapshot` commits.** The UPDATE would sit in the snapshot's WAL after the checkpoint, outside the `project.db` the autosave flushes - the one value in the snapshot a power cut could lose. The optional `stampOverride` inside the same transaction costs one branch.
- **Refuse edits while the recovery question is unanswered.** It would make the question modal for every edit action; the unresolved marker keeps the question honest across restarts without changing what the user may do meanwhile.
