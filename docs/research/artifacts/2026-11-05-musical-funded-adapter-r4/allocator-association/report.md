# Default scalar-new and handler association, revision 1

The named default allocator/handler chain can be qualified without invoking a
setter or forcing allocation failure. Current file evidence identifies the
scalar-new provider in the actual MSVC dynamic-runtime archive, the MSVCP public
handler exports and the UCRT query/callback guard. This report closes only the
source/body correspondence established below; eventual combined R3 linkage and
actual loaded-module association remain separate facts.

No existing source, probe, accepted ADR, proof, catalogue or binding was edited.
No program, allocator, math operation, setter, trap or failure injection was run
by this review. All native listings were generated by root from existing files.

## Source chain and its normal/failure alternatives

Installed `crt/src/vcruntime/new_scalar.cpp` defines scalar
`void* __cdecl operator new(size_t)`. It calls malloc(size), returns the pointer
on success, otherwise calls `_callnewh(size)`. A zero return throws bad_alloc
(or bad_array_new_length for SIZE_MAX); nonzero retries malloc. This is the
actual scalar-new source, not an invented allocator callback policy.

Installed release `_malloc_base` source calls HeapAlloc, returns a successful
block, and on failure either returns nullptr when new-mode is0 or consults
`_callnewh`; a failed handler sets ENOMEM and returns nullptr. A null handler
therefore invokes no application callback even if new-mode permits the extra
handler check. No assumption that `_set_new_mode` is absent is needed. The
source's ordinary HeapAlloc/API contract remains the heap boundary; no claim
about hidden native request counts or errno preservation is made.

Original Clock construction uses ordinary owning allocations before prefix
computation. Its small fixed object, shared control and bounded row/double
allocations have no custom allocator argument or application callback. A successful
Clock does not by itself reveal which allocations failed/retried. This report
supplies no measured allocation counts or failed-allocation site observations.

Installed UCRT `heap/new_handler.cpp` initializes two-state handler storage to
encoded nullptr. `_query_new_handler` locks, selects the current state, decodes
and returns its pointer, then unlocks. `_callnewh` obtains that pointer and
returns0 if null, before invoking it. With a nonnull pointer, it invokes the
callback and reports whether the callback returned nonzero; a callback may throw.
The C `_set_new_handler` implementation is the explicit mutation path.

Installed `crt/src/stl/stdhndlr.cpp` has a distinct zero-initialized C++ handler
and mutex. `std::get_new_handler` reads under the mutex. `std::set_new_handler`
stores its argument and registers a C bridge (or nullptr) with `_set_new_handler`.
The bridge invokes the C++ handler and returns1. A C++ getter returning nullptr
alone does **not** establish that a separately registered C handler is null.
The closed-source argument must cover both setter APIs and startup state.

The other inspected libvcruntime.lib/vcruntime.lib/msvcprt.lib listings do not

first jump to malloc at+0x1A; null branches to `_callnewh` at+0xE; zero handler
result branches to the SIZE_MAX test and the two named throw helpers; nonzero
returns to malloc. A nonnull malloc result returns. The source's terminal throw
helpers are followed by unreachable trap padding; no trap was executed or used
as an expected test result. No FP/control/FMA selector instruction occurs in
this member. Symbols/relocations identify the actual callees, not just similar
displayed instruction bytes.

The existing GUI import table has `_callnewh`, malloc/free and no direct DLL
operator-new import. That is consistent with linked scalar-new glue, but it
does not prove which archive member was selected into a historical image. The

Candidate MSVCP140.dll has ImageBase0x180000000 and exports
`std::get_new_handler` at RVA0x172A0 and `std::set_new_handler` at0x17300.
The pinned msvcprt.lib supplies their import symbols. Candidate MSVCP's import

Root's bounded candidate MSVCP listing associates the source bodies structurally:

The final bounded listing shows setter thunk0x609CE jumping to IAT0x63468.

## Inspected UCRT bodies

The pinned candidate ucrtbase.dll has `_query_new_handler` RVA0x5130. Its inspected
body obtains a lock, gets the dual-state index, reads slot array0x1398A0, decodes
using the security cookie, unlocks and returns. The adjacent initializer at
RVA0x5190 stores its encoded-null argument into both slots. The adjacent setter
at0x51B0 locks and writes the selected same array, returning the old decoded
pointer. These instructions correspond to the installed source's separate
initializer/query/set roles.

`_callnewh` at RVA0x5240 calls that query, tests the returned pointer, and returns0
directly when null. Its indirect callback instruction is strictly on the nonnull
branch. After a callback returns, it converts the returned integer to Boolean.
These inspected bodies contain no FP arithmetic/control instruction or reference
to the separate FMA3 dispatch dword at RVA0x139E60. Locks/state-index helpers are
ordinary CRT/runtime transfers, not application new-handler callbacks.

This is a source/emitted-code argument for the named candidate file. It does not
claim that a current GUI process was launched or that a previous/future binary
loaded it. A compatible filename or installed source directory is not a complete
loaded-runtime or patched-body identity.

## Conditional closure of the original allocation interval

The earlier pinned application corpus covers3,125 source files, all25 actual
application/JUCE TUs plus two static dependency TUs, and every selected dependency
source root as a conservative superset. It contains no C or C++ new-handler setter
and no FMA3 writer. JUCE allocation hooks are disabled; no plugin-host module is
linked. CRT source and its documented startup contract put initial handler/FMA
state before ordinary captured-request worker work.

Under the associated default scalar-new/UCRT/MSVCP source/API contracts, and
that closed admitted caller set, both handlers remain at their initial null
state. Thus any failed scalar-new call reaches the null `_callnewh` branch,
invokes no application new-handler callback and throws instead of retrying due
to a callback. On a successful returned allocation, ordinary Windows x64 ABI
control-preservation applies before the later original prefix arithmetic.
There is no application callback in this interval that can change the global
FMA3 selection. This is the supported conditional interval argument; endpoint
snapshots alone cannot supply it.

No FMA3 protection is inferred from ABI control preservation: the global selector
is a different object. If a future admitted source installs a nonnull handler,
its concrete body must separately preserve controls and avoid a selection write.
The current proof does not need an adversarial-module exclusion experiment or
a new runtime synchronization design. Ordinary source/API contracts are its scope.

## Closed narrow premise and remaining combined qualification

The archive member's source/symbol/relocation/instruction correspondence, candidate
MSVCP read/store/bridge/C-setter correspondence and candidate UCRT null callback
guard are now directly associated. Under their ordinary stock-runtime contracts
and the previously pinned closed application source, they close this particular
allocation/new-handler interval premise. A successful default-new return cannot
have run an application new-handler when the initial null state has no reachable
setter. An actual failed default-new entry terminates through the null-handler
failure branch instead of invoking or retrying after a callback. This is source/
body reasoning, not an inferred old allocation trace or empirical OOM result.

No further broad vendor disassembly or deliberate allocation failure is necessary
to establish this conditional premise. Unexpected runtime substitutions would
fail its named source/library/module identity, rather than being excused by an
uncheckable Boolean or an imagined environment-interference requirement.
